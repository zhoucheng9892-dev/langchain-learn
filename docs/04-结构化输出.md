# 第 4 章 结构化输出：把"一段话"变成"一个对象"

> 本章代码：`chapters/ch04_structured/01_with_structured_output.py`、`02_agent_structured.py`、`03_extraction_pipeline.py`

## 4.1 本章目标

- 用 Pydantic 定义输出结构，拿到校验过的对象而不是字符串
- 分清**模型级**和 **Agent 级**两种结构化输出的适用场景
- 掌握 DeepSeek 上的两个专属陷阱及其解法

## 4.2 模型级：with_structured_output

```python
from pydantic import BaseModel, Field

class Movie(BaseModel):
    title: str = Field(description="电影中文名")
    year: int = Field(description="上映年份")
    rating: float = Field(description="豆瓣评分 0-10")

movie = model.with_structured_output(Movie).invoke("推荐一部 2020 年后的科幻片")
print(movie.title, movie.rating)   # 已经是 Movie 实例
```

底层是把 schema 转成工具定义，让模型"调用这个工具"，再从参数里取结构化数据。所以它**只有一次模型调用**，不能查资料、不能调工具。

`include_raw=True` 会返回三个键：`raw`（原始 AIMessage）、`parsed`（解析结果）、`parsing_error`（解析错误）。排查"为什么字段是空的"时非常有用。

## 4.3 Agent 级：response_format

需要"先查资料，再按格式输出"时用 Agent：

```python
from langchain.agents.structured_output import ToolStrategy

agent = create_agent(
    model=get_model(),
    tools=[get_stock_price],
    response_format=ToolStrategy(StockReport),
)
result = agent.invoke({"messages": [...]})
result["structured_response"]   # StockReport 实例
```

两种策略的区别：

| 策略 | 机制 | 适用 |
| --- | --- | --- |
| `ProviderStrategy` | 用供应商原生 `response_format`（json_schema） | OpenAI 等支持原生结构化输出的模型 |
| `ToolStrategy` | 强制模型调用一个"输出工具" | 大多数模型，兼容性最好 |

**坑 1**：直接传 Pydantic 类时，框架可能选 `ProviderStrategy`，DeepSeek 不支持 → 400 `This response_format type is unavailable now`。
**解法**：显式写 `ToolStrategy(Schema)`。

**坑 2**：`ToolStrategy` 会强制 `tool_choice`，而**思考模式不支持强制 `tool_choice`** → 400 `Thinking mode does not support this tool_choice`。
**解法**：`reasoning_effort="none"`（`get_model()` 默认已关）。

两个坑叠在一起，就是本项目反复强调的那句话：

> **DeepSeek 上做结构化输出 = 关闭思考 + `ToolStrategy`。**

## 4.4 schema 怎么设计才好用

| 手段 | 写法 | 效果 |
| --- | --- | --- |
| 字段描述 | `Field(description="...")` | 模型按描述取值，描述越具体越准 |
| 枚举 | `Literal["a","b"]` 或 `Enum` | 杜绝自由发挥 |
| 数值约束 | `Field(ge=1, le=5)` | 越界会被 Pydantic 拦下 |
| 默认值 | `Field(default_factory=list)` | 容忍模型不给该字段 |
| 嵌套 | `list[Chapter]` | 支持复杂结构 |
| 业务校验 | `@field_validator` | 拦住"上限小于下限"这类模型不懂的规则 |

最重要的一个模式，来自 `03_extraction_pipeline.py`：

```python
class JobPost(BaseModel):
    is_job_post: bool = Field(description="这段文本是否真的是招聘信息")
    company: str = Field(default="", ...)
```

**先让模型判断"是不是"，再让它抽取。** 不加这个字段时，喂一段无关文本，模型会硬套 schema，编出"未知公司 / 月薪 1k"这种垃圾数据。加了之后，无关文本会被直接丢弃。

## 4.5 流水线三段式

真实业务里结构化输出很少一次成功，标准套路：

1. **schema 写约束**：枚举、范围、必填——减少模型犯错空间；
2. **Pydantic 校验业务规则**：上下限、日期先后、编码格式；
3. **逐条处理 + 失败兜底**：一批数据里坏一条不能炸整批。

```python
for text in batch:
    job = extract(text)          # 内部 try/except
    if job is None:
        dead_letter.append(text)  # 进人工复核队列
        continue
    rows.append(job)
```

`ToolStrategy(handle_errors=True)`（默认开启）会在校验失败时把错误信息回灌给模型重试一次，能救回大部分格式错误。

## 4.6 什么时候不用结构化输出

- 只是给人看的回答 → 不需要，多一层反而限制表达
- 输出本身就是长文/代码 → 用普通消息，事后解析
- 模型不支持工具调用 → 只能用 json_mode 或提示词约束（可靠性差很多）

## 4.7 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 400 `tool_choice` | 思考模式 + 强制工具 | `reasoning_effort="none"` |
| 400 `response_format type unavailable` | 走了 ProviderStrategy | `ToolStrategy(Schema)` |
| 字段全是空/默认值 | schema 描述太模糊 | 每个字段都写 `description` |
| 无关文本也被抽成对象 | 缺少"是否相关"判断字段 | 加 `is_xxx: bool` |
| 偶发解析失败 | 模型输出截断 | 提高 `max_tokens` |
