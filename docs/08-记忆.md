# 第 8 章 记忆：短期、长期与压缩

> 本章代码：`chapters/ch08_memory/01_sqlite_persistence.py`、`02_long_term_memory.py`、`03_summarization.py`

## 8.1 本章目标

- 分清三种"记忆"，知道每种该存什么
- 用 SQLite checkpointer 做跨进程的短期记忆
- 用 Store 做跨会话的长期记忆
- 用摘要中间件解决上下文爆炸

## 8.2 三种记忆，别混用

| 类型 | 载体 | 生命周期 | 存什么 |
| --- | --- | --- | --- |
| 短期记忆 | checkpointer（按 `thread_id`） | 一次会话 | 对话历史、工具结果 |
| 长期记忆 | store（按 namespace + key） | 永久 | 用户偏好、画像、历史订单 |
| 外部知识 | 向量库 / 文件 | 永久 | 文档、FAQ、知识库（第 10 章） |

判断标准一句话：**下次用户换个话题、隔一周再来，这条信息还该不该在？**
该在 → store；不该在 → checkpointer。

## 8.3 短期记忆落盘：SQLite checkpointer

```python
import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

conn = sqlite3.connect(".data/checkpoints.db", check_same_thread=False)
agent = create_agent(..., checkpointer=SqliteSaver(conn))
```

`check_same_thread=False` 是必须的：LangGraph 可能在不同线程里用同一个连接。

实测（`01_sqlite_persistence.py`）：第一次运行聊两句写入磁盘，第二次**新进程**加 `--read` 读回 4 条消息，内容一字不差。

生产换 Postgres：

```python
from langgraph.checkpoint.postgres import PostgresSaver
with PostgresSaver.from_conn_string(DSN) as saver:
    saver.setup()
    agent = create_agent(..., checkpointer=saver)
```

## 8.4 长期记忆：Store

```python
from langgraph.store.memory import InMemoryStore

@tool
def save_preference(key: str, value: str, runtime: ToolRuntime[UserContext]) -> str:
    runtime.store.put(("preferences", runtime.context.user_id), key, {"value": value})
    return f"已记住：{key}={value}"

@tool
def recall_all(runtime: ToolRuntime[UserContext]) -> str:
    items = runtime.store.search(("preferences", runtime.context.user_id))
    return "；".join(f"{it.key}={it.value['value']}" for it in items)

agent = create_agent(..., tools=[save_preference, recall_all], store=InMemoryStore())
```

store 的寻址方式是 **namespace（元组）+ key**：

```
namespace = ("preferences", "u_001")
key       = "咖啡"
value     = {"value": "不加糖"}
```

实测效果：

```
[1] 用户: 我喝咖啡不加糖，喜欢燕麦奶     -> 工具写入两条
[3] 换 thread 后: 老样子，来一杯          -> "一杯不加糖、燕麦奶的咖啡"
[4] 换用户 u_002: 来杯美式               -> 反问"要加糖吗"（互不干扰）
```

**关键认知：store 不会自动进模型上下文。** 必须由工具主动 `search` 出来，或用中间件在 `before_model` 里注入。这是很多人以为"接了 store 就自动有记忆"的误区。

## 8.5 上下文爆炸：摘要中间件

对话一长，`messages` 会撑爆上下文。两种应对：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 裁剪 `trim_messages` | 丢掉老消息 | 忘事（第 3 章实测：数字全错） |
| 摘要 `SummarizationMiddleware` | 把老消息压成一段摘要 | 一次额外模型调用 |

```python
SummarizationMiddleware(
    model=get_model(max_tokens=512),
    trigger=("messages", 8),   # 超过 8 条触发
    keep=("messages", 2),      # 保留最近 2 条原文
)
```

三种 `trigger`：

| 写法 | 含义 | 适用 |
| --- | --- | --- |
| `("messages", 8)` | 消息条数 | 简单直观，离线调试 |
| `("tokens", 4000)` | token 数 | 贴近真实成本，推荐 |
| `("fraction", 0.8)` | 上下文窗口占比 | 换模型不改配置 |

实测（`03_summarization.py`）：6 轮对话后消息数从 12 降到 6，压缩后的摘要里**保住了全部 5 个关键约束**（3000 预算、春熙路、不吃辣、投影仪、11 月 5 日）。

这就是摘要相对裁剪的价值：**信息密度换长度，而不是直接丢弃**。

## 8.6 组合使用的推荐架构

```
用户请求
  -> 中间件：从 store 读出用户画像，注入 system prompt
  -> 模型：基于 摘要 + 最近 N 条 + 画像 生成
  -> 工具：把新的稳定事实写回 store
  -> checkpointer：保存本次会话历史
```

四条经验：

1. **store 里的东西要"值得存"**：稳定的偏好、身份、长期目标，不要存一次性信息；
2. **写 store 要有触发条件**：别每句话都写，让模型判断"这是长期偏好"；
3. **摘要阈值别调太低**：每次摘要都是一次模型调用，太频繁反而更贵；
4. **给用户"忘记我"的能力**：合规要求，也是信任基础。

## 8.7 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 重启后记忆没了 | `InMemorySaver` | 换 SQLite/Postgres |
| 接了 store 但模型不知道 | store 不自动进上下文 | 工具检索或中间件注入 |
| 摘要后关键信息丢了 | `keep` 太小 / 摘要提示词不合适 | 调大 `keep`，自定义 `summary_prompt` |
| SQLite 报线程错误 | 缺 `check_same_thread=False` | 加上 |
| 记忆串用户 | namespace 没带 user_id | 每个用户独立 namespace |
