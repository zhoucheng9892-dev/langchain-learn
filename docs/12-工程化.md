## 12.1 本章目标

- 用 CallbackHandler 统计 token、耗时、工具调用
- 搭一个最小可用的评测回归集
- 用缓存和上下文管理把成本压下去

## 12.2 三个必须回答的问题

上线后你一定会被问：

1. 这次请求花了多少钱？→ **成本可观测**
2. 为什么这个 case 答错了？→ **链路可追溯**
3. 改了提示词，效果变好了吗？→ **评测可回归**

没有这三样，优化全靠猜。

## 12.3 可观测：CallbackHandler

```python
class MetricsHandler(BaseCallbackHandler):
    def on_chat_model_start(self, serialized, messages, **kwargs):
        self.llm_calls += 1
        self._t0 = time.perf_counter()

    def on_llm_end(self, response, **kwargs):
        self.total_ms += (time.perf_counter() - self._t0) * 1000
        tokens = (response.llm_output or {}).get("token_usage", {})
        self.prompt_tokens += tokens.get("prompt_tokens", 0)
        self.completion_tokens += tokens.get("completion_tokens", 0)

    def on_tool_start(self, serialized, input_str, **kwargs):
        self._t0 = time.perf_counter()

    def on_tool_end(self, output, **kwargs):
        name = kwargs.get("name")
        self.tool_calls[name] += 1
        self.tool_ms[name] += (time.perf_counter() - self._t0) * 1000
```

挂上去：

```python
agent.invoke({...}, config={"callbacks": [handler], "run_name": "refund-flow"})
```

实测输出：

```
模型调用 2 次，累计 2313ms
token: 输入 800 / 输出 113
估算成本: ¥0.000626
工具 search_order: 1 次，累计 51ms
```

并且和 `usage_metadata` 交叉验证**完全一致**（800/113）——两个来源对得上，说明统计没错。

### 该埋哪些点

| 层级 | 字段 |
| --- | --- |
| 请求级 | `thread_id`、`user_id`、模型名、总 token、总耗时、是否命中缓存 |
| 模型级 | 每次调用的输入/输出 token、首字延迟、`finish_reason` |
| 工具级 | 工具名、参数摘要、耗时、成功/失败、错误类型 |
| 异常 | `run_id`、堆栈、当时的输入摘要 |

### LangSmith：改环境变量就行

```ini
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=lsv2_xxx
LANGSMITH_PROJECT=langchain-deepseek-learning
```

不用改代码，所有调用自动上报。本地 handler 负责实时打点与告警，LangSmith 负责事后追溯，两者不冲突。

## 12.4 评测：最小可用回归集

三步：

1. **数据集**：20~50 条真实问题，带关键词或标准答案；
2. **打分器**：能规则判定就别上模型；
3. **报告**：通过率 + 失败样本。

```python
DATASET = [
    {"q": "create_agent 取代了哪个旧函数？", "must": ["create_react_agent"]},
    {"q": "旧代码放到哪个包了？", "must": ["langchain-classic"]},
    ...
]

ok, missing = score_by_keywords(answer, case["must"])
```

实测（`02_eval.py`）：

```
1. [PASS] create_agent 取代了哪个旧函数？
2. [PASS] 旧代码放到哪个包了？
3. [PASS] trigger 支持哪几种阈值？
4. [PASS] 生产环境 recursion_limit 一般设多少？
5. [FAIL] 人工审批的 decisions 里有哪几种 type？
   答案: 资料中未提及。
   缺少关键词: ['approve']

通过率 4/5 = 80%
```

**这个 FAIL 非常有价值**：不是模型不会答，而是**检索没召回**那段资料。看失败样本能直接定位到"该调切分/检索"，而不是"去改提示词"——这就是评测的意义。

### LLM-as-judge：只给主观题用

```python
class JudgeResult(BaseModel):
    score: int = Field(ge=1, le=5)
    reason: str
```

三个纪律：

- 必须给**明确的评分标准**（5 分/4 分/3 分各是什么）；
- 模型判定有方差，关键结论跑 3 次取均值；
- judge 用的模型不应和被测模型完全相同（否则容易自洽）。

## 12.5 省钱：四件事

### ① 缓存

```python
from langchain_core.caches import InMemoryCache
from langchain_core.globals import set_llm_cache
set_llm_cache(InMemoryCache())
```

实测：

```
第 1 次(未命中): 1170ms  token=703
第 2 次(命中)  :   1.0ms  token=703（直接返回，不产生费用）
耗时下降三个数量级
```

三种缓存层次：

| 类型 | 命中条件 | 注意 |
| --- | --- | --- |
| 精确缓存 | 输入字符串完全一致 | 本例；闲聊场景命中率低 |
| 语义缓存 | 向量相似度超阈值 | 要自己实现，有误命中风险 |
| 前缀缓存 | 相同前缀（供应商侧） | DeepSeek/OpenAI 自动打折，无需改代码 |

### ② 上下文裁剪

用摘要代替全量历史（第 8 章），或 `trim_messages` 兜底（第 3 章）。这一项通常省得最多。

### ③ 输出上限

`max_tokens` 一定要设。Agent 的中间步骤很容易写出 2000 字废话。

### ④ 模型分流

简单问题走便宜模型，复杂问题走强模型：

```python
ModelFallbackMiddleware  # 反过来用：主用强模型，失败/超时降级
```

或自己做一个路由：先用小模型判断难度，再选模型。

### 成本估算表（实测数据）

| 场景 | 输入 | 输出 | 单次费用 |
| --- | --- | --- | --- |
| 单轮问答 | 800 | 120 | ¥0.0006 |
| RAG 问答（3 段上下文） | 3000 | 200 | ¥0.0019 |
| Agent 两轮工具 | 2400 | 300 | ¥0.0018 |
| 客服机器人 1 万次/天 | 4000 | 250 | **¥25/天** |

结论：**吃掉预算的是"每天多少次"，不是"单次多贵"。** 优化重点在缓存命中率和上下文长度。

## 12.6 上线检查清单

| 项 | 检查点 |
| --- | --- |
| 密钥 | 不硬编码，走环境变量 / 密钥管理 |
| 超时 | 每次调用设 `timeout`，工具也有超时 |
| 重试 | `max_retries` + `ToolRetryMiddleware`，注意幂等 |
| 限流 | `ToolCallLimitMiddleware` + `recursion_limit` |
| 兜底 | 捕获 `GraphRecursionError`、超时、工具异常 |
| 记忆 | 多副本用外部 checkpointer |
| 观测 | callback 打点 + LangSmith 追踪 |
| 评测 | 20+ 条回归集，改一次跑一次 |
| 成本 | 缓存 + 上下文裁剪 + `max_tokens` |
| 合规 | PII 脱敏、日志脱敏、"忘记我"能力 |

## 12.7 从 0.x 迁移的机械步骤

```bash
# 1. 装 v1 和 classic（读旧代码用）
uv add langchain langchain-classic
```

| 旧写法 | 新写法 |
| --- | --- |
| `from langchain.chains import LLMChain` | `prompt \| model` |
| `from langchain.retrievers import ...` | `from langchain_classic.retrievers import ...` |
| `create_react_agent(prompt=...)` | `create_agent(system_prompt=...)` |
| `pre_model_hook=` | `middleware=[before_model(...)]` |
| `ToolNode(handle_tool_errors=...)` | `ToolErrorMiddleware` |
| `langchain.retrievers.MultiQueryRetriever` | `langchain_classic.retrievers` |
| `langchain.hub` | `langchain_classic.hub` |

原则：**classic 包用来读旧代码，新代码一律用 v1 写法。** 机械替换 `langchain.` → `langchain_classic.` 能让老项目跑起来，但不是让你继续那么写。

## 12.8 练习

1. 把 `MetricsHandler` 改成同时统计"首字延迟"（`on_llm_new_token`）。
2. 给评测集加 5 条你业务里的真实问题，跑出基线通过率。
3. 打开缓存，用同一个问题问 3 次，统计第 2、3 次的实际耗时。
4. 把项目里某个 0.x 风格的 Chain 改写成 v1 写法（或反过来，用 classic 跑通一段老代码）。

---

## 结语

到这里，LangChain 1.x 的完整能力地图就走完了：

```
模型 → 消息 → 结构化输出 → 工具 → Agent → 中间件 → 记忆 → 流式 → RAG → 多 Agent → 工程化
```

如果只能记住三件事：

1. **`create_agent` + 中间件**是 v1 的全部骨架；
2. **能用一次模型调用解决的，不要上 Agent**；
3. **可观测、可评测、可回滚**，比任何提示词技巧都重要。

剩下的，去写你自己的项目吧。
