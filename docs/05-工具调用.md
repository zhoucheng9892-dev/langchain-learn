# 第 5 章 工具调用：Agent 的手脚

> 本章代码：`chapters/ch05_tools/01_tool_basics.py`、`02_tool_runtime.py`、`03_tool_errors.py`

## 5.1 本章目标

- 写一个模型能正确调用的工具（docstring 与 schema 是重点）
- 用 `ToolRuntime` 安全地拿到用户身份、会话状态
- 把"业务失败 / 偶发失败 / 代码失败"分开处理

## 5.2 工具是什么

工具 = **一份给模型看的 JSON Schema** + **一个可执行函数**。`@tool` 做的就是这件事：

```python
@tool
def get_weather(city: str) -> str:
    """查询指定城市的当前天气。"""   # <- 这段 docstring 是给模型看的
    return "晴，25°C"

get_weather.name            # "get_weather"
get_weather.description     # "查询指定城市的当前天气。"
get_weather.args_schema     # Pydantic 模型，会被转成 JSON Schema 发给模型
```

**docstring 不是注释，是 API 文档。** 模型看不到你的实现，只能看名字、描述、参数 schema。所以：

- 名字用动词短语：`search_docs` 比 `docs` 好
- 描述说清"做什么、返回什么、什么时候该用"
- 参数用 `Field(description=...)` 逐个说明

参数复杂时用 `args_schema`：

```python
class SearchInput(BaseModel):
    query: str = Field(description="搜索关键词，尽量具体")
    top_k: int = Field(default=3, ge=1, le=10)
    category: Literal["news", "docs", "blog"] = "docs"

@tool("search_knowledge", args_schema=SearchInput)
def search_knowledge(query, top_k=3, category="docs"): ...
```

`Literal` 特别有用：把"可选值"写进 schema，模型就不会编出 `category="paper"`。

## 5.3 手写一遍 Agent 循环

`create_agent` 内部就是这段：

```python
model_with_tools = model.bind_tools(tools)
messages = [HumanMessage("...")]

while True:
    ai = model_with_tools.invoke(messages)
    messages.append(ai)
    if not ai.tool_calls:
        break
    for call in ai.tool_calls:
        messages.append(tool_map[call["name"]].invoke(call))  # 传整个 ToolCall
```

注意 `tool.invoke(call)` 传的是**整个 ToolCall 字典**，不是参数 dict——这样返回的 `ToolMessage` 才会自动带上正确的 `tool_call_id`。

自己写这 15 行的价值：出问题时你知道该看哪里。`create_agent` 额外补的是状态管理、最大轮数、并行执行、错误处理、持久化、中间件钩子。

## 5.4 ToolRuntime：不暴露给模型的运行时信息

问题：工具怎么知道"当前用户是谁"？

**错误做法**：把 `user_id` 写成工具参数。模型可以随便填别人的 id，既不安全也不可靠。

**正确做法**：`ToolRuntime`，由框架注入，模型完全看不见。

```python
@dataclass
class UserContext:
    user_id: str
    plan: str

@tool
def who_am_i(runtime: ToolRuntime[UserContext]) -> str:
    """查询当前用户身份。"""
    return runtime.context.user_id

agent = create_agent(..., tools=[who_am_i], context_schema=UserContext)
agent.invoke({...}, context=UserContext(user_id="u_1", plan="pro"))
```

`runtime` 上能拿到的东西：

| 属性 | 内容 | 用途 |
| --- | --- | --- |
| `runtime.context` | 本次调用的上下文对象 | 用户身份、租户、权限 |
| `runtime.state` | 会话状态（含 `messages`） | 读历史、计数器 |
| `runtime.store` | 长期记忆存储 | 读写跨会话数据（第 8 章） |
| `runtime.tool_call_id` | 本次调用 id | 构造自定义 ToolMessage |
| `runtime.stream_writer` | 写 custom 流事件 | 工具进度上报（第 9 章） |

**这是把"权限校验"放在代码层而不是提示词层的关键机制。** 提示词可以被绕过，`if runtime.context.plan != "pro": return "拒绝"` 不会。

## 5.5 工具失败的三种类型

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| 业务性失败 | 查不到订单、无权限、参数不合理 | **别抛异常**，`return "未找到订单"`，模型会转述 |
| 偶发性失败 | 网络超时、429 限流 | `ToolRetryMiddleware` 自动重试 |
| 代码性失败 | `KeyError`、除零、外部契约变更 | `ToolErrorMiddleware` 统一兜底 + 告警 |

```python
# 1) 业务失败
return f"未找到订单 {order_id}，请确认订单号。"

# 2) 偶发失败：指数退避重试
middleware=[ToolRetryMiddleware(max_retries=3, initial_delay=0.2, backoff_factor=2.0)]

# 3) 代码失败：翻译成模型能懂的话
def on_error(exc, request):
    return f"工具执行失败（{type(exc).__name__}），请换一种方式或告知用户。"

middleware=[ToolErrorMiddleware(on_error)]
```

`03_tool_errors.py` 里做了对比实验：**不装 `ToolErrorMiddleware` 时，工具抛异常会让整轮 `invoke` 直接崩掉**，用户看到的是 500。这是生产事故的常见来源。

## 5.6 工具设计的一些经验

| 原则 | 说明 |
| --- | --- |
| 一个工具一件事 | `search_and_summarize` 不如 `search` + 让模型总结 |
| 返回文本要短 | 工具返回 5000 字会把上下文挤爆，做截断或分页 |
| 工具数量 ≤ 10 | 超过 10 个，选择准确率明显下降，考虑拆成多 Agent（第 11 章） |
| 幂等 | Agent 可能重复调用，写操作要能去重 |
| 错误信息要可读 | 模型会照着你的错误信息决定下一步 |

## 5.7 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 工具从不被调用 | docstring 太含糊 / 描述没提使用场景 | 重写描述，明确"何时使用" |
| 参数类型错 | 用了 `dict` 之类的宽泛类型 | 用 Pydantic `args_schema` |
| 一轮崩掉 | 工具抛异常 | `ToolErrorMiddleware` |
| 模型反复调同一个工具 | 返回值没用 / 没给出结论 | 返回明确结果，或加 `ToolCallLimitMiddleware` |
| 拿到别人的数据 | 把身份做成参数 | 改用 `ToolRuntime.context` |
