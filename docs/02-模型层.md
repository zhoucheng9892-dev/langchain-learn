## 2.1 本章目标

- 掌握创建模型的三种方式，知道什么时候用哪种
- 理解 `reasoning_effort` 对输出、成本、能力的影响
- 会用异步并发，把 5 次串行调用压成 1 次等待

## 2.2 三种创建方式

```python
# A. 字符串引用（配置驱动，换模型不改代码）
from langchain.chat_models import init_chat_model
model = init_chat_model("deepseek:deepseek-flash", temperature=0)

# B. 直接实例化（参数最全）
from langchain_deepseek import ChatDeepSeek
model = ChatDeepSeek(model="deepseek-flash", temperature=0, max_tokens=256, max_retries=3)

# C. 项目工厂（推荐，收敛配置）
from langchain_learn import get_model
model = get_model()
```

字符串写法的格式是 `provider:model`，LangChain 会据此自动 import 对应的集成包。`create_agent(model=...)` 两种都接受——传字符串时框架内部帮你实例化。

**建议**：业务代码里统一用工厂函数（方式 C），把模型名、温度、重试、思考开关集中在一处。等到哪天要换模型或调参，只改一个文件。

## 2.3 参数速查

| 参数 | 作用 | 实践建议 |
| --- | --- | --- |
| `model` | 模型 ID | 必须是 API 认的名字，不是产品名 |
| `temperature` | 随机性，0~2 | 抽取/分类用 0，创意写作用 1.0+ |
| `max_tokens` | 输出上限 | 一定设，防止失控生成；开思考时至少 1024 |
| `reasoning_effort` | 思考强度 | `"none"` 关闭，`"high"` 加强 |
| `max_retries` | SDK 层重试 | 生产设 2~3，配合超时 |
| `timeout` | 单次请求超时 | 30~60 秒，长任务另算 |
| `top_p` | 核采样 | 通常不用动，和 temperature 二选一调 |

`temperature=0` 也不是绝对确定：它只是让采样趋向最高概率，供应商侧仍可能有微小波动。要真正可复现，用缓存（第 12 章）。

## 2.4 思考模式：v4 的关键特性

DeepSeek v4 系列默认开启思考：模型先输出一段推理过程（`reasoning_content`），再给答案。

```python
msg = get_model(thinking=True, max_tokens=2048).invoke("三管同开多久注满水池？")
msg.content                                        # 最终答案
msg.additional_kwargs["reasoning_content"]         # 思考过程
msg.usage_metadata["output_token_details"]["reasoning"]  # 思考用了多少 token
```

三个直接影响：

1. **成本**：思考也计费，计入输出 token。
2. **延迟**：思考越久，首字越慢。
3. **能力限制**：**思考模式不支持强制 `tool_choice`**。这会导致 `with_structured_output` 直接 400（第 4 章会复现）。

### 很隐蔽的坑：`max_tokens` 太小，答案为空

```python
model = get_model(thinking=True, max_tokens=20)
msg = model.invoke("9.11 和 9.9 哪个大？")
print(repr(msg.content))                    # ''
print(msg.usage_metadata)                   # output_tokens=20, reasoning=20
```

思考把 20 个 token 用完了，正文一个字都没轮到，`finish_reason` 是 `length`。**看到空回答先查 `finish_reason` 和 reasoning token，不要怀疑模型坏了。**

### 决策建议

| 任务 | 思考开关 | 理由 |
| --- | --- | --- |
| 抽取、分类、格式转换 | 关 | 快、便宜、结构化输出才可用 |
| 客服问答、RAG | 关 | 有资料兜底，不需要长推理 |
| 数学、复杂代码、多步规划 | 开 | 准确率提升明显 |
| 批量离线处理 | 关 | 成本敏感 |

## 2.5 流式与并发

```python
# 流式：chunk.content 是增量片段
for chunk in model.stream("列出三个学习建议"):
    print(chunk.content, end="", flush=True)

# 并发：5 个请求重叠等待，实测提速 4~5 倍
import asyncio
results = await asyncio.gather(*(model.ainvoke(q) for q in questions))
```

实测数据（本项目 `03_async_concurrency.py`）：串行 8.2s → 并发 1.75s，提速 4.7 倍。

**Windows 上有个坑**：一个进程里反复调用 `asyncio.run()` 并复用同一个 httpx 客户端，退出时会报 `RuntimeError: Event loop is closed`。把所有异步任务放进**同一个** `asyncio.run()` 里就不会出现。

并发要有上限：

```python
sem = asyncio.Semaphore(2)   # 最多 2 个请求同时在飞

async def limited(q):
    async with sem:
        return await model.ainvoke(q)
```

生产上限通常取供应商限额的 60%~70%，配合 `max_retries` 处理偶发 429。

## 2.6 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 模型名 400 | 用了产品名 | 查供应商文档的 model ID |
| 答案为空 | `max_tokens` 被思考吃光 | 提高上限或关思考 |
| 结构化输出 400 `tool_choice` | 思考模式 + 强制调用 | `reasoning_effort="none"` |
| `Event loop is closed` | 多次 `asyncio.run` 复用客户端 | 合并到一个事件循环 |
| 并发被限流 | 无上限 | `Semaphore` + 重试退避 |
